## 第1章 Docker 是什么 — 用"集装箱"类比建立直觉

> **💡 一句话总结：Docker 是软件世界的"集装箱"，把应用和环境打包在一起，到处都能跑。**

### 🎯 为什么需要 Docker？

想象一个场景：

> 小明在自己的电脑上开发了一个网站，运行得很好。他把代码发给同事小红，结果小红的电脑上运行不了。
> 
> 小明说："奇怪，在我电脑上明明可以跑啊！"

这个问题在软件开发中非常常见，被称为 **"环境一致性问题"**。

为什么会这样？因为每个人的电脑环境不同：

- 操作系统版本不一样（Windows 10 vs Windows 11）
- 安装的软件版本不一样（Python 3.8 vs Python 3.11）
- 配置文件不一样
- 依赖库不一样

**Docker 就是为了解决这个问题而诞生的。**

### 💡 一个类比：集装箱

在没有集装箱之前，运输货物是这样的：

```
散装运输时代：
┌─────────────────────────────────────┐
│  货物A：需要冷藏    → 需要专门的冷藏车  │
│  货物B：需要防潮    → 需要专门的防潮箱  │
│  货物C：需要轻拿轻放 → 需要专门的保护   │
└─────────────────────────────────────┘
问题：每种货物都需要专门的运输方式，效率低、成本高
```

有了集装箱之后：

```
集装箱时代：
┌─────────────────────────────────────┐
│  把货物装进标准集装箱                 │
│  ↓                                  │
│  集装箱自带保护功能（防潮、冷藏等）     │
│  ↓                                  │
│  可以用任何船、火车、卡车运输          │
│  ↓                                  │
│  到哪里都能直接卸货使用                │
└─────────────────────────────────────┘
```

**Docker 就是软件世界的"集装箱"！**

它把你的应用程序和它需要的一切（代码、依赖库、配置文件、运行环境）打包到一个"集装箱"里。这个集装箱可以在任何电脑上运行，不用担心环境问题。

### 🐍 最小必要知识

**一句话定义：**

> Docker 是一个开源的容器化平台，它把应用程序及其依赖打包到一个轻量级、可移植的容器中，确保应用在任何环境中都能以相同的方式运行。

**Docker 名字的由来：**

> 🎓 **趣味知识**：Docker 这个名字来自"Dock Worker"（码头工人）。就像码头工人把货物装进集装箱一样，Docker 把软件装进"容器"。创始人 Solomon Hykes 在 2013 年的 PyCon 大会上首次提出这个概念，从此改变了软件部署的方式。

**三个关键词：**

| 关键词 | 解释          | 类比             |
| --- | ----------- | -------------- |
| 容器化 | 把应用和环境打包在一起 | 把货物装进集装箱       |
| 轻量级 | 不需要完整的操作系统  | 集装箱比整艘船轻很多     |
| 可移植 | 可以在任何电脑上运行  | 集装箱可以用任何交通工具运输 |

### 🤖 真实场景

**场景1：开发环境统一**

```
没有 Docker 时：
开发者A：我的电脑是 Python 3.8，跑通了
开发者B：我的电脑是 Python 3.11，报错了
开发者C：我的电脑是 Python 3.9，部分功能有问题
→ 需要花大量时间解决环境问题

有了 Docker 后：
所有人用同一个 Docker 容器
→ 环境完全一致，代码直接跑
```

**场景2：快速部署**

```
传统部署：
1. 购买服务器
2. 安装操作系统
3. 安装 Python
4. 安装依赖库
5. 配置环境变量
6. 上传代码
7. 测试运行
→ 可能需要几天时间

Docker 部署：
1. 购买服务器
2. 安装 Docker
3. 运行 Docker 容器
→ 几分钟搞定
```

**场景3：微服务架构**

```
一个电商网站可能有：
- 用户服务（处理登录注册）
- 商品服务（展示商品信息）
- 订单服务（处理下单）
- 支付服务（处理付款）

每个服务都是一个独立的 Docker 容器：
┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐
│ 用户服务 │ │ 商品服务 │ │ 订单服务 │ │ 支付服务 │
└─────────┘ └─────────┘ └─────────┘ └─────────┘

好处：
- 每个服务可以独立更新
- 某个服务挂了，不影响其他服务
- 可以根据负载单独扩展某个服务
```

## 第2章 容器 vs 虚拟机 — 两种"搬家"方式的区别

> **💡 一句话总结：虚拟机是"整栋房子搬家"，Docker 是"只搬需要的东西"。**

### 🎯 为什么需要了解这个区别？

你可能听说过"虚拟机"（Virtual Machine），它也是一种让软件在隔离环境中运行的技术。

很多人会问："既然有虚拟机了，为什么还需要 Docker？"

理解它们的区别，能帮你明白 Docker 的价值在哪里。

### 💡 一个类比：两种搬家方式

**虚拟机 = 整栋房子搬家**

```
虚拟机搬家方式：
┌─────────────────────────────────────┐
│  要搬的东西：一个书架                 │
│                                     │
│  虚拟机的做法：                       │
│  1. 把整个房子拆下来                  │
│  2. 包括地基、墙壁、屋顶              │
│  3. 连同房子里面的所有家具一起搬       │
│  4. 到新地方重新盖一栋一模一样的房子   │
│                                     │
│  结果：为了搬一个书架，搬了一整栋房子  │
└─────────────────────────────────────┘
```

**Docker 容器 = 只搬需要的东西**

```
Docker 搬家方式：
┌─────────────────────────────────────┐
│  要搬的东西：一个书架                 │
│                                     │
│  Docker 的做法：                     │
│  1. 把书架打包好                     │
│  2. 只带书架和书                     │
│  3. 到新地方，借用当地的房间          │
│  4. 把书架放进去就能用                │
│                                     │
│  结果：只搬需要的东西，轻便高效        │
└─────────────────────────────────────┘
```

### 🐍 最小必要知识

**核心区别：共享 vs 独立**

| 特性       | 虚拟机（VM）        | Docker 容器     |
| -------- | -------------- | ------------- |
| **包含内容** | 完整的操作系统 + 应用   | 只有应用 + 依赖     |
| **大小**   | GB 级别（几个G）     | MB 级别（几十到几百M） |
| **启动时间** | 分钟级            | 秒级            |
| **资源占用** | 多（每个VM都要完整的OS） | 少（共享主机的操作系统）  |
| **隔离程度** | 强（完全独立）        | 中等（进程级隔离）     |

**架构对比图：**

```
虚拟机架构：
┌─────────────┐ ┌─────────────┐ ┌─────────────┐
│   应用 A     │ │   应用 B     │ │   应用 C     │
├─────────────┤ ├─────────────┤ ├─────────────┤
│  依赖库 A    │ │  依赖库 B    │ │  依赖库 C    │
├─────────────┤ ├─────────────┤ ├─────────────┤
│  Guest OS   │ │  Guest OS   │ │  Guest OS   │  ← 每个VM都有自己的操作系统
├─────────────┴─┴─────────────┴─┴─────────────┤
│              Hypervisor（虚拟化层）           │
├─────────────────────────────────────────────┤
│              Host OS（主机操作系统）           │
├─────────────────────────────────────────────┤
│              硬件                            │
└─────────────────────────────────────────────┘

Docker 容器架构：
┌─────────────┐ ┌─────────────┐ ┌─────────────┐
│   应用 A     │ │   应用 B     │ │   应用 C     │
├─────────────┤ ├─────────────┤ ├─────────────┤
│  依赖库 A    │ │  依赖库 B    │ │  依赖库 C    │
├─────────────┴─┴─────────────┴─┴─────────────┤
│              Docker Engine（容器引擎）        │
├─────────────────────────────────────────────┤
│              Host OS（主机操作系统）           │  ← 所有容器共享同一个操作系统
├─────────────────────────────────────────────┤
│              硬件                            │
└─────────────────────────────────────────────┘
```

**关键区别：**

- 虚拟机：每个应用都需要一个完整的操作系统（Guest OS）
- Docker：所有应用共享主机的操作系统（Host OS）

这就是为什么 Docker 更轻量、更快的原因！

### 🤖 真实场景

**场景：一台服务器能跑多少应用？**

```
假设服务器有 16GB 内存：

用虚拟机：
- 每个虚拟机需要 2GB 内存（包括操作系统）
- 最多跑 8 个虚拟机
- 实际用于应用的内存：8 × 0.5GB = 4GB

用 Docker：
- 每个容器需要 0.5GB 内存（不需要操作系统）
- 最多跑 32 个容器
- 实际用于应用的内存：32 × 0.5GB = 16GB

结论：同样硬件资源，Docker 能跑 4 倍的应用！
```

**场景：启动速度对比**

```
虚拟机启动：
1. 加载操作系统（30秒）
2. 启动系统服务（20秒）
3. 启动应用（10秒）
→ 总计：1分钟

Docker 容器启动：
1. 启动应用（2秒）
→ 总计：2秒

差距：30倍！
```

**什么时候用虚拟机？什么时候用 Docker？**

| 场景          | 推荐使用   | 原因                    |
| ----------- | ------ | --------------------- |
| 需要运行不同操作系统  | 虚拟机    | Docker 只能运行和主机相同系统的应用 |
| 需要强隔离（如多租户） | 虚拟机    | 虚拟机隔离更彻底              |
| 快速部署应用      | Docker | 启动快、资源少               |
| 微服务架构       | Docker | 轻量、易扩展                |
| 开发测试环境      | Docker | 快速创建和销毁               |

### ✏️ 小练习

**练习1：Docker 容器比虚拟机轻量的原因是什么？**

<details>
<summary>点击查看答案</summary>

Docker 容器比虚拟机轻量的原因是：**所有容器共享主机的操作系统**。

虚拟机每个都需要一个完整的操作系统（Guest OS），而 Docker 容器不需要，它们直接使用主机的操作系统（Host OS）。

这就像：

- 虚拟机：每个人都要带自己的房子
- Docker：大家合租一栋房子，各住各的房间

</details>

**练习2：以下场景应该用虚拟机还是 Docker？**

场景：你要在一个 Windows 服务器上运行一个 Linux 专用的应用程序。

<details>
<summary>点击查看答案</summary>

应该用**虚拟机**。

原因：Docker 容器只能运行和主机相同操作系统的应用。如果主机是 Windows，Docker 容器里的应用也只能是 Windows 应用。

要运行 Linux 应用，需要用虚拟机来创建一个 Linux 环境。

（注：Docker Desktop 在 Windows/Mac 上使用了轻量级虚拟机来运行 Linux 容器，但这是另一个话题了）

</details>

## 第3章 镜像 Image — 菜谱

> **💡 一句话总结：镜像是只读的"菜谱"，定义了如何构建一个完整的运行环境。**

### 🎯 为什么需要镜像？

想象你要做一道菜：

```
做菜需要什么？
1. 食材清单（需要什么材料）
2. 做法步骤（怎么处理食材）
3. 调料配方（用什么调料、放多少）

如果你把这些都写成一份菜谱，那么：
- 任何人拿到菜谱，都能做出一模一样的菜
- 菜谱可以分享给别人
- 可以根据菜谱做出很多份相同的菜
```

**Docker 镜像就是"菜谱"！**

它包含了运行一个应用需要的所有信息：

- 代码
- 依赖库
- 配置文件
- 运行环境

### 💡 一个类比：菜谱

```
Docker 镜像 = 菜谱
┌─────────────────────────────────────┐
│  菜名：Python Web 应用               │
│                                     │
│  食材清单：                           │
│  - Python 3.11                      │
│  - Flask 2.0                        │
│  - requests 2.28                    │
│                                     │
│  做法步骤：                           │
│  1. 安装 Python                     │
│  2. 安装依赖库                       │
│  3. 复制代码                         │
│  4. 设置环境变量                     │
│  5. 启动应用                         │
│                                     │
│  特点：                               │
│  - 只读（不能修改）                   │
│  - 可以分享给别人                     │
│  - 可以做出很多份                     │
└─────────────────────────────────────┘
```

### 🐍 最小必要知识

**镜像的特点：**

| 特点  | 解释           | 类比          |
| --- | ------------ | ----------- |
| 只读  | 创建后不能修改      | 菜谱印好后不能改    |
| 分层  | 由多层叠加而成      | 菜谱可以有多个步骤   |
| 可分享 | 可以上传到仓库      | 菜谱可以发给别人    |
| 可复用 | 一个镜像可以创建多个容器 | 一份菜谱可以做很多份菜 |

**镜像的分层结构：**

```
Docker 镜像的分层：
┌─────────────────────────────────────┐
│  第5层：你的代码                     │  ← 最终的应用
├─────────────────────────────────────┤
│  第4层：安装依赖库                   │
├─────────────────────────────────────┤
│  第3层：安装 Python                  │
├─────────────────────────────────────┤
│  第2层：系统配置                     │
├─────────────────────────────────────┤
│  第1层：基础操作系统（Ubuntu）        │  ← 基础镜像
└─────────────────────────────────────┘

为什么要分层？
- 如果两份菜谱都用到"基础酱汁"，只需要保存一份
- 修改上层时，不需要重新构建下层
- 下载时可以只下载变化的部分
```

**Dockerfile — 菜谱的写法：**

```dockerfile
# 这是一个 Dockerfile，用来描述如何构建镜像
# 就像写菜谱一样

# 第1步：选择基础镜像（相当于选择基础食材）
FROM python:3.11-slim

# 第2步：设置工作目录（相当于准备厨房）
WORKDIR /app

# 第3步：复制依赖文件（相当于准备食材清单）
COPY requirements.txt .

# 第4步：安装依赖（相当于处理食材）
RUN pip install -r requirements.txt

# 第5步：复制代码（相当于把菜的做法写进去）
COPY . .

# 第6步：设置启动命令（相当于告诉别人怎么开始做）
CMD ["python", "app.py"]
```

### 🤖 真实场景

**场景：从 Docker Hub 获取现成的镜像**

```
Docker Hub 就像一个"菜谱图书馆"，里面有成千上万的现成镜像。

常见镜像：
- python:3.11    → Python 开发环境
- nginx:latest   → 网页服务器
- mysql:8.0      → 数据库
- redis:7        → 缓存数据库

获取镜像的命令：
docker pull python:3.11

这就像从图书馆借一本菜谱。
```

**场景：构建自己的镜像**

```
当你需要一个定制的环境时，可以自己写 Dockerfile 构建镜像。

构建命令：
docker build -t my-app:1.0 .

这就像根据自己的需求写一本新菜谱。
```

### ✏️ 小练习

**练习1：Docker 镜像和容器的关系是什么？**

<details>
<summary>点击查看答案</summary>

Docker 镜像和容器的关系就像**菜谱和菜**的关系：

- **镜像（Image）**：是只读的模板，包含运行应用需要的所有东西
- **容器（Container）**：是镜像的运行实例，就像根据菜谱做出来的菜

一个镜像可以创建多个容器，就像一份菜谱可以做出很多份相同的菜。

</details>

**练习2：为什么要使用基础镜像（如 `python:3.11-slim`）？**

<details>
<summary>点击查看答案</summary>

使用基础镜像的原因：

1. **省时**：不需要从零开始构建，已经有了操作系统和基本工具
2. **省空间**：基础镜像经过优化，体积小
3. **标准化**：使用官方镜像，确保质量和安全
4. **可复用**：可以基于同一个基础镜像构建多个不同的应用

就像做菜时，你可以选择：

- 从零开始种菜、养鸡（太慢）
- 去超市买现成的食材（快速、方便）

</details>

## 第4章 容器 Container — 做出来的菜

> **💡 一句话总结：容器是镜像的运行实例，就像根据菜谱做出来的菜，可以吃、可以有很多份。**

### 🎯 为什么需要容器？

有了菜谱（镜像），我们还需要把菜做出来（容器）。

```
菜谱（镜像）的作用：
- 定义"怎么做"
- 可以分享、复用
- 只是蓝图，不能吃

做出来的菜（容器）：
- 可以吃（可以运行）
- 可以有很多份（一个镜像可以创建多个容器）
- 吃完了就没了（容器可以删除）
```

**容器是镜像的运行实例！**

### 💡 一个类比：做出来的菜

```
镜像 vs 容器：
┌─────────────────────────────────────┐
│  镜像（菜谱）                        │
│  - 只读，不能修改                    │
│  - 可以长期保存                      │
│  - 可以分享给别人                    │
└─────────────────────────────────────┘
          ↓ 创建
┌─────────────────────────────────────┐
│  容器（做出来的菜）                   │
│  - 可以运行（可以吃）                │
│  - 有生命周期（可以启动、停止、删除）  │
│  - 可以有多个（一份菜谱做很多份菜）   │
└─────────────────────────────────────┘
```

### 🐍 最小必要知识

**容器的生命周期：**

```
容器的状态变化：

    创建（Created）
         ↓
    启动（Running） ←───── 重启（Restarting）
         ↓                       ↑
    暂停（Paused）               │
         ↓                       │
    继续（Running） ─────────────┘
         ↓
    停止（Exited）
         ↓
    删除（Removed）
```

**容器的特点：**

| 特点  | 解释                     |
| --- | ---------------------- |
| 轻量  | 启动快，资源占用少              |
| 隔离  | 每个容器独立，互不影响            |
| 可移植 | 可以在任何支持 Docker 的机器上运行  |
| 临时性 | 容器删除后，里面的数据会丢失（除非特别配置） |

**常用命令：**

```bash
# 创建并启动一个容器
# docker run [镜像名]
docker run -d nginx
# -d 表示在后台运行

# 查看正在运行的容器
docker ps

# 停止容器
# docker stop [容器ID或名称]
docker stop my-nginx

# 启动已停止的容器
docker start my-nginx

# 删除容器
docker rm my-nginx
```

### 🤖 真实场景

**场景1：运行一个网页服务器**

```bash
# 一行命令启动一个 nginx 网页服务器
docker run -d -p 8080:80 --name my-web nginx

# 解释：
# -d：后台运行
# -p 8080:80：把主机的 8080 端口映射到容器的 80 端口
# --name my-web：给容器起个名字
# nginx：使用的镜像

# 现在打开浏览器访问 http://localhost:8080 就能看到 nginx 的欢迎页面
```

**场景2：运行一个 Python 应用**

```bash
# 运行一个 Python 容器
docker run -it python:3.11 python

# 解释：
# -it：交互模式，可以输入命令
# python:3.11：使用的镜像
# python：要运行的命令

# 现在你在容器里的 Python 环境中，可以写 Python 代码了
```

**场景3：容器的数据持久化**

```bash
# 问题：容器删除后，里面的数据会丢失
# 解决：使用"数据卷"把数据保存到主机上

docker run -d -v /host/data:/container/data mysql

# 解释：
# -v /host/data:/container/data
# 把主机的 /host/data 目录映射到容器的 /container/data 目录
# 这样即使容器删除，数据还在主机上
```

### ✏️ 小练习

**练习1：镜像和容器的区别是什么？**

<details>
<summary>点击查看答案</summary>

| 对比项  | 镜像（Image） | 容器（Container） |
| ---- | --------- | ------------- |
| 是什么  | 只读的模板     | 镜像的运行实例       |
| 状态   | 静态，不能运行   | 动态，可以运行       |
| 生命周期 | 长期保存      | 可以创建、启动、停止、删除 |
| 数量   | 一个镜像      | 可以创建多个容器      |
| 类比   | 菜谱        | 做出来的菜         |

</details>

**练习2：为什么容器是"临时性"的？这样设计有什么好处？**

<details>
<summary>点击查看答案</summary>

容器是临时性的，意味着：

- 容器删除后，里面的数据会丢失
- 每次启动容器，都是全新的状态

这样设计的好处：

1. **一致性**：每次启动都是相同的状态，不会有"上次运行留下的脏数据"
2. **可预测**：应用的行为完全由镜像决定
3. **易扩展**：可以快速创建新的容器，不用担心状态同步
4. **易恢复**：容器挂了？删掉重建一个新的就好

如果需要保存数据，可以使用"数据卷"把数据持久化到主机上。

</details>

## 第5章 仓库 Registry — 菜谱共享平台

> **💡 一句话总结：仓库是存储和分享镜像的平台，就像"菜谱图书馆"。**

### 🎯 为什么需要仓库？

有了菜谱（镜像），怎么分享给别人？

```
没有仓库时：
- 把菜谱（镜像）用U盘拷给别人 → 麻烦
- 把菜谱（镜像）上传到网盘 → 不专业、不安全
- 手动告诉别人怎么做 → 效率低

有了仓库后：
- 把菜谱（镜像）上传到仓库 → 专业、安全
- 别人从仓库下载 → 方便、快速
- 可以管理不同版本 → 有序
```

**Docker 仓库就是"菜谱共享平台"！**

### 💡 一个类比：菜谱共享平台

Docker Hub（最大的公开仓库）：

└─────────────────────────────────────┘

## 第8章 新手避坑指南 — 少走弯路

> **💡 一句话总结：提前知道这些常见错误，能帮你节省大量调试时间。**

### 🎯 为什么需要避坑指南？

新手在学习 Docker 时，经常会遇到一些"坑"。这些坑可能让你卡很久，甚至怀疑人生。

提前知道这些坑，能帮你：

- 节省调试时间
- 避免重复犯错
- 更快上手 Docker

### 🐍 常见错误及解决方案

### 🤖 真实场景

**场景：新手最容易踩的 3 个坑**

```
坑1：数据丢失
新手想法："容器就是我的服务器，数据放里面就行"
结果：容器重启后，数据全没了
教训：一定要用数据卷持久化重要数据

坑2：端口冲突
新手想法："8080 端口应该没人用吧"
结果：报错 "port is already allocated"
教训：先用 netstat 或 lsof 检查端口占用

坑3：镜像太大
新手想法："直接用 ubuntu 镜像，什么都装"
结果：镜像 1GB+，构建慢、拉取慢
教训：使用 slim 或 alpine 版本的基础镜像
```

**坑1：容器内的文件修改不会保存到镜像**

```
❌ 错误想法：
"我进入容器修改了配置文件，然后重新运行容器，修改应该还在吧？"

✅ 正确理解：
容器是临时的，删除后修改会丢失。
如果需要保存修改，应该：
1. 修改 Dockerfile，重新构建镜像
2. 使用数据卷把配置文件映射到主机
```

**坑2：端口冲突**

```
❌ 错误现象：
docker run -d -p 8080:80 nginx
报错：Bind for 0.0.0.0:8080 failed: port is already allocated

✅ 原因：
主机的 8080 端口已经被其他程序占用

✅ 解决方法：
1. 换一个端口：docker run -d -p 8081:80 nginx
2. 找出占用端口的程序并停止它
```

**坑3：忘记加 -d 参数**

```
❌ 错误现象：
docker run nginx
然后终端被占用了，按 Ctrl+C 容器就停了

✅ 正确做法：
docker run -d nginx
-d 表示后台运行
```

**坑4：不指定镜像版本号**

```
❌ 错误做法：
docker pull python
→ 会拉取 python:latest，但 latest 可能不是你想要的版本

✅ 问题：
- latest 标签会随时间变化，今天是 3.12，明天可能是 3.13
- 不同时间拉取的镜像版本可能不同
- 可能导致"在我电脑上可以跑，你那不行"的问题

✅ 正确做法：
docker pull python:3.11
明确指定版本号，确保环境一致
```

**坑5：容器内无法访问主机服务**

```
❌ 错误现象：
在容器内访问 localhost:3306 连接主机的 MySQL，连接失败

✅ 原因：
容器内的 localhost 指的是容器自己，不是主机

✅ 解决方法：
1. 使用主机的 IP 地址（不是 localhost）
2. 使用 Docker 的 host 网络模式
3. 使用 Docker Compose 管理多个服务
```

**坑6：构建镜像时 COPY 失败**

```
❌ 错误现象：
COPY failed: file not found in build context

✅ 原因：
Dockerfile 中 COPY 的文件不在构建上下文中

✅ 解决方法：
1. 确保文件在 Dockerfile 所在目录
2. 检查 .dockerignore 文件是否排除了该文件
3. 使用正确的相对路径
```

**坑7：容器启动后立即退出**

```
❌ 错误现象：
docker run -d my-app
然后 docker ps 看不到容器

✅ 原因：
容器的主进程退出了，容器也就停止了

✅ 解决方法：
1. 查看容器日志：docker logs <容器ID>
2. 确保 Dockerfile 中的 CMD 是一个长期运行的进程
3. 使用 -it 参数进入容器调试
```

**坑8：数据丢失**

```
❌ 错误现象：
删除容器后，数据库里的数据全没了

✅ 原因：
容器是临时的，删除后数据会丢失

✅ 解决方法：
使用数据卷持久化数据：
docker run -d -v /host/data:/container/data mysql
```

### ✏️ 小练习

**练习1：为什么容器内的修改不会保存到镜像？**

<details>
<summary>点击查看答案</summary>

因为**镜像是只读的**，容器只是镜像的一个运行实例。

当你运行一个容器时，Docker 会在镜像的基础上创建一个"可写层"。你在容器内的修改（如修改文件、安装软件）都保存在这个可写层中。

当你删除容器时，这个可写层也会被删除，所以修改就丢失了。

如果需要保存修改，应该：

1. 修改 Dockerfile，重新构建镜像
2. 使用 `docker commit` 把容器保存为新镜像（不推荐）
3. 使用数据卷把数据持久化到主机

</details>

**练习2：如何避免"在我电脑上可以跑"的问题？**

<details>
<summary>点击查看答案</summary>

使用 Docker 可以完全避免这个问题！

具体做法：

1. 把应用和所有依赖打包到 Docker 镜像中
2. 使用 Dockerfile 定义构建过程
3. 把 Dockerfile 和代码一起提交到版本控制
4. 在任何地方都使用相同的镜像运行

这样，无论在谁的电脑上、在什么环境中，运行的都是完全相同的环境。

</details>

### 常见问题 FAQ

**Q1：Docker 免费吗？**

A：Docker 本身是开源免费的。Docker Hub 提供免费账户，可以存储有限的私有镜像。企业使用可能需要付费。

**Q2：Docker 能在 Windows 上运行吗？**

A：可以。Docker Desktop 支持 Windows 和 Mac。在 Windows 上，Docker 会使用轻量级虚拟机来运行 Linux 容器。

**Q3：学习 Docker 需要编程基础吗？**

A：不需要。Docker 是一个工具，主要用来部署和管理应用。了解基本的命令行操作会更有帮助。

**Q4：Docker 和 Kubernetes 是什么关系？**

A：Docker 用来打包和运行单个容器，Kubernetes 用来管理成百上千个容器。可以理解为：Docker 是"厨师"，Kubernetes 是"餐厅经理"。

**Q5：镜像和容器的关系是什么？**

A：镜像是只读的模板，容器是镜像的运行实例。一个镜像可以创建多个容器。就像菜谱和菜的关系。
